# EnviroIQ — ESG Sustainability Platform

## Overview

EnviroIQ is a real-time multi-tenant ESG sustainability measurement platform. It enables companies to track CO2 emissions from fleet vehicles and energy consumption. The platform features custom passwordless authentication, a super-admin portal, generates board-ready PDF reports, includes an embeddable public widget, incorporates full audit logging for SOC 2 compliance, and supports role-based access.

Key capabilities include:
- **ESG Intelligence**: Maturity Scoring, Emission Target management, and Scenario Modelling for emission reduction.
- **Data Ingestion**: Integration with GPS providers (Navman, Blackhawk) for fleet data and PDF/email parsing for energy bills.
- **Reporting & Analytics**: Dashboard widgets for maturity and target progress, detailed emission tracking, and concrete, ranked decarbonisation recommendations.

The project aims to provide comprehensive ESG data and actionable insights to facilitate sustainable practices and drive environmental impact.

## System Architecture

The EnviroIQ platform is built as a pnpm monorepo using Node.js 24 and TypeScript 5.9.

### Technical Implementations
- **API Framework**: Express 5, secured with Helmet and express-rate-limit.
- **Database**: PostgreSQL with Drizzle ORM. The schema includes tables for organisations, users, fleet, energy, goals, reports, widgets, and audit logs.
- **Authentication**: Custom passwordless system using `express-session` for session management. It supports four sign-in methods: magic links (via Resend), WebAuthn passkeys (using `@simplewebauthn/server` and `@simplewebauthn/browser`), Google SSO and Microsoft SSO (native OIDC + PKCE via `jose`, no Clerk/Auth0/WorkOS). SSO never creates accounts (no JIT) — the user must already exist; the first successful sign-in links a row in `sso_identities`. Org admins can configure per-org policy in **Settings → Sign-in & SSO**: enable/disable each provider, restrict the list of allowed sign-in methods, optionally require one specific SSO provider for non-admin users. Per-user overrides for `requiredSignInProvider` and `allowedSignInMethods` are also supported via the per-user "Sign-in restrictions" dialog and a bulk action on the Admin → Users page (`POST /organisations/:orgId/users/sign-in-policy/bulk`) that applies the same override to many users at once with per-user lock-out validation and one `user.sign_in_policy.changed` audit event per affected user. Org admins always retain a magic-link break-glass path (audited as `auth.break_glass_magic_link`). All SSO and policy events are written to the audit log (`sso.sign_in.success`, `sso.sign_in.rejected`, `sso.identity.linked`, `sso.policy.changed`). Users can rename their own passkeys via `PATCH /auth/passkeys/:id` (owner-only, max 64 chars, `null`/blank clears the label) — shown as an inline rename action on the Account page and audited as `auth.passkey.renamed`.
- **Validation**: Zod is used for schema validation.
- **API Codegen**: Orval generates API client code from an OpenAPI specification.
- **Monorepo Structure**: Organized into `artifacts` (API server and frontend), `lib` (API spec, generated clients, database schema), and `scripts`.
- **Roles**: `super_admin`, `org_admin`, and `org_viewer` with distinct access levels.
- **Emission Factors**: Pre-defined factors for Diesel, Petrol, Electricity, and Gas are used for CO2e calculations.
- **Compliance Document Archive**: Ingested documents are archived in the `document_archives` table with a 6-month retention policy, aligned with NZ Privacy Act, GDPR, and SOC 2. Metadata is retained indefinitely for audit purposes.
- **Security Features**: Includes a runtime security status check (`/security/status`) available to admins, assessing various security configurations and practices. Public compliance snapshots are also available.
- **Notifications (foundation)**: Two-table system in `lib/db/src/schema/notifications.ts` — `notification_events` (one row per domain event, `dedupe_key` UNIQUE for idempotency) and `notifications` (one row per recipient, joined back via `source_event_id`). Fan-out is centralised in `artifacts/api-server/src/lib/notifications.ts` (`notify(...)`); the event insert and recipient fan-out run inside a single `db.transaction()` so a fan-out failure rolls back the dedupe row and the next call can retry cleanly. v1 recipient policy: every active `org_admin`/`super_admin` in the org; if the org has zero eligible admins, fall back to platform `super_admin`s and tag the category with `orphaned_org_no_admins`. Severity=error sends one batched Resend call per fan-out covering all recipients (`sendNotificationEmailBatch` in `mailer.ts`, chunked at the 100/call Resend batch limit) — never N separate sends. The batch returns a per-item `results` array (`{ ok: true }` ONLY when Resend confirmed dispatch); the fan-out and digest paths use that to stamp `email_sent_at` exclusively for confirmed sends — anything else (provider error, dev-console fallback, missing config in production, no-id-returned partial) stays unstamped so the next digest tick can retry, preventing silent drops. Severity=warn rolls up into one per-user digest, dispatched **per-org at the org's local 8am**: `scheduler.ts` ticks hourly and walks every organisation, firing `sendNotificationDigests({ organisationId })` only when that org's `default_timezone` (defaults to Pacific/Auckland) reports hour=8 (per-org `lastDigestDay` guard prevents duplicates inside a local day). First-sign-in gate: users with `lastLoginAt IS NULL` still receive in-app bell rows but are excluded from the email batch — their warn rows stay unstamped so they roll into a future digest after sign-in. **Audit-row anchoring (all paths)**: every notify-emitting code path in `routes/energy.ts` and `routes/fleet.ts` persists a failure (or success-with-warn) audit row first via `await logAudit({...})` (which returns the audit id), then passes that id as `sourceAuditId` AND as the dedupe-key anchor for every event — including the webhook rejection paths (`webhook.fleet.invalid_api_key:{provider}:{auditId}`, `webhook.fleet.device_not_registered:{orgId}:{provider}:{deviceId}:{auditId}`) — so each distinct failure produces its own bell row and only true retries of the same audit id coalesce. Calendar-day dedupe caps were deliberately removed in favour of per-event audit-id anchoring so admins always see the true volume of misrouted/rejected traffic. Failure sources wired: `routes/energy.ts /upload` (parse errors → error, low-confidence reviewFlags → warn — both keyed on the audit id), `routes/fleet.ts` webhooks (navman/blackhawk/generic — `invalid_api_key`/`invalid_token` → **error** alerting platform super_admins via `organisationId: "PLATFORM"` sentinel using the immediate batched-email path, `device_not_registered` → warn alerting org admins, both audit-id anchored), `routes/fleet.ts /import-km` (per-row skips → warn keyed on success audit id, crash → error keyed on failure audit id). When fan-out falls back to platform super_admins (the source org has zero eligible admins, or the source org is the `PLATFORM` sentinel for webhook bad-credentials alerts), the recipient bell row is filed under each super_admin's own home `organisationId` so it surfaces in their normal in-app context — the parent `notification_events` row keeps the original source `organisationId` and the recipient row's `category` is suffixed `(orphaned_org_no_admins)` so platform ops can see what the source was. Read API at `/api/organisations/:orgId/notifications` (list / unread-count / :id/read / :id/dismiss / mark-all-read) — every route enforces `requireAuth + requireOrgAccess` and additionally constrains `recipientUserId = req.user.id` so users only ever see their own notifications. The list endpoint supports `category`, `severity`, `status` (`unread`/`read`/`all`), `page`, and `limit` query params. UI surface: bell icon in `app-layout.tsx` header (popover, polling `/unread-count` every 60s, latest 10 items) + full `/notifications` inbox page with severity/status/category filters (Unread only / Read only / All; categories populated dynamically) and prev/next pagination controls (25 per page; auto-resets to page 1 on filter change). No per-user prefs UI in v1. Self-heal in `index.ts → ensureNotificationsSchema()` includes `CREATE TABLE IF NOT EXISTS` plus `ALTER TABLE … ADD COLUMN IF NOT EXISTS` guards for every column on both tables so a partial earlier deploy can heal forward without manual DDL. **Nightly gap detector** (`artifacts/api-server/src/lib/notification-gap-scanners.ts`, started by `startGapDetector()` in `index.ts`): a timezone-aware daily worker that ticks every hour and fires the full per-org scan exactly once per local day at the configured local hour (default **06:00 Pacific/Auckland**, both overridable via `GAP_DETECTOR_HOUR`/`GAP_DETECTOR_TZ` env vars). Idempotency is two-layered: an in-memory `lastDailyRunYmd` short-circuits repeat ticks within the same process, and a **DB-backed claim** (`tryClaimDailyRun`) inserts a sentinel row into `notification_events` keyed on `gap_detector:run:{tz}:{ymd}` with `ON CONFLICT DO NOTHING` — the UNIQUE constraint on `dedupe_key` makes the claim atomic, so a process restart mid-window (or any future horizontal scale-out to multiple replicas) sees the existing marker and skips, never producing same-day duplicate fires. The marker rows are intentionally orphan (zero recipients), which `resolveDedupeKey` already suppresses, so they never surface to users. The scan walks every active org and emits warn-severity notifications for three classes of "data we expected but didn't see":

- `missing_bill` — for every (utility_type, provider) account that produced ≥1 reading inside the trailing 12 **completed** calendar months (`period_start >= horizon AND period_start < cutoff` where `cutoff` is the first day of the current month), find the missing months. The `< cutoff` clamp prevents brand-new accounts whose first reading is in the current month from synthesizing a bogus 12-month backlog. Implemented as **one set-based SQL query** (CTE: accounts × generate_series(months) LEFT JOIN energy_readings WHERE r.id IS NULL) — no per-account N+1 fanout. Emits **one notification per (account, month) gap** with dedupe key `missing_bill:{orgId}:{utilityType}:{provider}:{yyyy-mm}` so each gap-month is its own bell row and back-filling one month doesn't hide other still-missing months.
- `stale_telematics` — active vehicles with `gpsProvider != 'none'` and zero `fleet_events` in the last 7 days. Emits **one notification per stale vehicle** with dedupe key `stale_telematics:{orgId}:{vehicleId}` (stable per-gap identity — a re-broken vehicle reuses the same key and re-fires only via `:v{N}` after dismissal; one vehicle recovering never affects its still-stale neighbours' bell rows).
- `overdue_report` — any quarter whose end + 14d grace has passed and which has no `reports` row with `status='ready'` covering that period. The status filter is required: reports in `'generating'` or `'failed'` state never produced a deliverable board pack, so they must NOT suppress the overdue notification (would be the exact silent miss this scanner exists to surface). Looks back up to 4 completed quarters; emits one notification per overdue quarter with dedupe key `overdue_report:{orgId}:{year}-Q{q}`.

Dedupe lifecycle (handled by `resolveDedupeKey`): first fire of a given base key creates a fresh event; while at least one recipient row is undismissed the next scan returns null (suppress); once every recipient row is dismissed the next scan bumps the suffix to `:v2`, `:v3`, … so a re-appearing gap re-fires as a new event. Orphan events (zero recipient rows — happens when the org had no eligible admins at fire time) are also suppressed to avoid an infinite re-fire loop. Per-org work runs inside its own try/catch so one failing org never blocks the rest. Admin endpoint `POST /api/admin/notifications/run-scanner?dryRun=true|false` (super_admin only, audit-logged) lets ops trigger an ad-hoc run and inspect the per-scanner counts; `dryRun=true` walks every org and returns the would-be-emitted summary without ever calling `notify()`.

### Schema changes

**Workflow when adding/altering tables or columns:**

1. Edit the relevant file under `lib/db/src/schema/` and re-export from `lib/db/src/schema/index.ts`.
2. Locally: run `pnpm --filter @workspace/db run push-force` to apply the change to your dev database, then `pnpm --filter @workspace/db run verify-schema` to confirm the database now matches the Drizzle schema (this same check runs on every server startup).
3. **Add a matching idempotent self-heal** in `artifacts/api-server/src/index.ts` (`ensureXxxSchema()`) using `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE … ADD COLUMN IF NOT EXISTS`. Wire it into the startup chain just before `verifyAndStart()`. This is what brings production into line — the post-merge script only touches the dev database.
4. Commit. Nothing else gets generated or committed.

**On merge** — `scripts/post-merge.sh` runs `drizzle-kit push --force` against the dev database and then `verify-schema`. Both must succeed or the merge fails.

**On every API server startup** — the `ensure*` chain runs first (so production DDL gets applied), then `verifyDatabaseSchema()` introspects every table declared in `lib/db/src/schema` against `information_schema`. If anything is missing, the server logs a structured FATAL with the missing tables/columns and exits non-zero — so a deploy with a missing column visibly fails its health check instead of returning 500s on the first request that touches it.

### Feature Specifications
- **ESG Intelligence**:
    - **Maturity Scoring**: A 4-dimensional system (Foundation, Coverage, Quality, Governance) resulting in grades: Foundation, Developing, Advanced, Leader.
    - **Emission Targets**: CRUD operations for defining reduction targets with baselines, target years, percentage reductions, and frameworks (SBTi, Paris). Progress is computed server-side in `artifacts/api-server/src/lib/target-progress.ts` against an annualised trailing-12-month figure (NOT the dashboard's selected period), with three modes — `collecting` (<3 months of data → no %), `estimated` (3-11 months → annualised + caveat), `actual` (12 months → exact TTM). Mode is driven by distinct calendar months that actually contain emission records, so an org that signs up early but logs sporadically is correctly downgraded to "estimated".
    - **Scenario Modelling**: An interactive engine for modeling emission reductions through levers like EV transition, distance reduction, modal shifts, renewables, efficiency, and offsets.
- **Decarbonisation Recommendations**: Concrete, ranked, NZ-specific actions generated from live fleet, energy, and target data, including CO₂e savings, capex, payback, scope, and effort.
- **ESG Board Pack PDF (`/api/orgs/:orgId/reports/:id/pdf`)**: Server-rendered HTML → PDF report for a quarter or year. The snapshot generator (in `artifacts/api-server/src/routes/reports.ts`) joins fleet events, vehicles, energy readings and goals, and stores the result on `reports.data_snapshot` (JSON). Two board-trust safeguards are baked in: (1) months without an uploaded power bill render as **"Awaiting bill"** and the Total CO₂e for that month excludes the gap (rather than recording zero) — a banner above the monthly table flags how many months are incomplete; (2) every emitter gets a **Fuel cost** column derived via a 3-tier fallback — actual `cost_nzd` when every event is invoiced → litres × NZ pump average for the uncosted share → km × `fuel_consumption_l_per_100km`/100 × pump average for the uncosted share. Estimated figures are flagged with `*` and a footnote referencing the NZ_DIESEL_PRICE / NZ_PETROL_PRICE module-level constants. The estimate prorates by uncosted-event share so actual invoiced costs are never dropped or double-counted, and electric / hydrogen / unknown fuel types render `—` rather than fabricating a diesel estimate. Snapshot fields are stored once at generation time, so reports created before this change must be regenerated to show the new columns.
- **CRM Integration API (`/api/v1/*`)**: A bearer-key authenticated API for customer operations, fully aligned with the FGC Customer Operations API Standard v1. It handles customer provisioning, contact/user management, subscriptions, billing, and pulls audit/ESG metrics. This API enforces specific response envelopes, error structures, correlation IDs, and idempotency keys. Lifecycle endpoints require specific `reason_code` values.

### Release Test Suite (`scripts/release-tests/`)
A tiered post-release smoke suite (pure Node 20, runs in <1s) gating the API after every deploy. **Three tiers, run via `pnpm release:test [-- --target=<url>] [-- --tier=boot|smoke|journey]`:**
- **Tier 1 — Boot** (~6 checks): `/api/healthz` 200 + cold-start budget, `/auth/session` 401, `/auth/sso/providers` 200, org-scoped + CRM `/v1/*` routers respond 401. No auth required. *Catches: dead server, broken auth middleware, route-mount typos.*
- **Tier 2 — Smoke** (~35 checks): Magic-link enumeration contract (bogus email → 200, malformed → 400), every major mounted router (26 org-scoped + 6 top-level + the POST-only `mission/generate`) returns 401/403 (not 404 = unmounted, not 500 = broken, not 2xx = auth bypass leak — the assertion is **strict**). Bonus `/v1/openapi.json` check when `RELEASE_TEST_BEARER` is set.
- **Tier 3 — Journey** (~8 checks): Two modes, picked automatically. **Local** (`DATABASE_URL` set + target is localhost or `*.replit.dev`/`*.repl.co`): forges a session by inserting a row directly into the `session` table and signing the `eiq.sid` cookie with `SESSION_SECRET`, then walks `/auth/session → /organisations → fleet/vehicles → energy/readings → emissions → reports → targets → recommendations`. Cleans up on exit. **Prod** (`RELEASE_TEST_BEARER` set): walks `/v1/openapi.json` + `/v1/customers`. Forge-mode is **hard-refused** against `.replit.app` / custom domains for safety; falls through to a clear SKIP. The shared `RateLimitedError` downgrades 429s from `/api/auth/*` (limiter is 20 hits per 15 min) to SKIP — but only for auth paths; 429s elsewhere still fail. Add new routers to `ORG_SCOPED_ROUTERS` in `02-smoke.mjs` with a `probe` sub-path (use `""` if the router has a `GET /` handler, otherwise something like `/vehicles`/`/summary`).
